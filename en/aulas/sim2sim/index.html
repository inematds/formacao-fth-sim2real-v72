Sim2sim as a gate before the robot

Before any robot, the policy has to pass in a second simulator and through the same message path the robot uses. It's the official unitree_rl_lab flow: train in Isaac Lab, validate in unitree_mujoco, and only then the G1. In this lesson you build that gate in three stages, with real DDS, and you see the error that most often brings policies down on this crossing.

Goal: run the policy through a three-stage gate: a different robot model and the manufacturer's DDS message path.

01 · The three-stage gate

Click each block in the diagram to see what it does.

02 · What the crossing tends to break

Real findings from building this gate (10/19/2026). Click each one.

1. Joint order

Isaac Lab orders the joints one way; the robot's SDK, another. The deploy.yaml carries the map (joint_ids_map), and each list comes in its own order: kp and kd in the robot's order, default pose and actions in Isaac Lab's order.

Getting this wrong brings the robot down in 1 s, in both simulators (common error below).

2. Step and integrator

unitree_mujoco comes with a 5 ms step and an Euler integrator. With the wrist kd = 10 (limit of 5 N·m on pitch and yaw), the PD oscillates and the arm stays at the torque limit the whole time. The gait does not suffer; the gate gives a warning, it does not fail.

With 1–2 ms, the warning goes away. It comes from the simulator, not the policy: check it before touching the training.

3. DDS on lo

The lo interface does not do multicast, and without multicast two DDS processes cannot find each other. The kit adds a fixed peer at 127.0.0.1 to the Unitree configuration (s2r.iniciar_dds) only when the interface is lo.

On the robot, the interface is the network card connected to it; the domain and the topics are the same.

4. CycloneDDS

The SDK asks for the Python package cyclonedds==0.10.2. On aarch64 there is no wheel: pip fails without the C library. The block builds the releases/0.10.x branch (5041f35) with cmake, in 1–2 min.

The C tag 0.10.2 aborted here with "buffer overflow detected". On x86_64, pip usually finds the wheel (reported, not tested here).

03 · Set up the manufacturer's path (once)

CycloneDDS 0.10.2, unitree_sdk2_python and unitree_mujoco, pinned to the tested commits. You need cmake and a C compiler if pip does not find a wheel.

Terminal · DDS + SDK + Unitree simulator
F=${FTH:-$HOME/fth}; cd $F && . .venv/bin/activate
pip install -q cyclonedds==0.10.2 2>/dev/null || {
  [ -d cyclonedds ] || git clone -q --filter=blob:none -b releases/0.10.x https://github.com/eclipse-cyclonedds/cyclonedds
  git -C cyclonedds checkout -q 5041f35
  cmake -S cyclonedds -B cyclonedds/build -DCMAKE_INSTALL_PREFIX=$F/cyclonedds/install -DBUILD_EXAMPLES=OFF > /dev/null
  cmake --build cyclonedds/build --target install -j 4 > /dev/null 2>&1
  export CYCLONEDDS_HOME=$F/cyclonedds/install && pip install -q cyclonedds==0.10.2; }
git -C cyclonedds log -1 --format="cyclonedds (C) %H (%ad)" --date=short 2>/dev/null | sed -E 's/([0-9a-f]{7})[0-9a-f]{33}/\1/'
[ -d unitree_sdk2_python ] || git clone -q https://github.com/unitreerobotics/unitree_sdk2_python
git -C unitree_sdk2_python checkout -q 814556d && pip install -q -e unitree_sdk2_python pygame
[ -d unitree_mujoco ] || git clone -q https://github.com/unitreerobotics/unitree_mujoco
git -C unitree_mujoco checkout -q 1eb6642 && git -C unitree_mujoco log -1 --format='unitree_mujoco %h (%ad)' --date=short
python3 -c "import importlib.metadata as m, unitree_sdk2py; print('cyclonedds', m.version('cyclonedds'), '· unitree_sdk2py ok')"

With --ordem sdk, the kit uses the default pose and the actions as if they were already in the robot's order. The G1 falls in 1 s in both models. If your policy falls as soon as it starts, check the map before anything else.
